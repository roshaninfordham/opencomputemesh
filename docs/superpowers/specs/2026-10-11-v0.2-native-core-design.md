# OpenComputeMesh v0.2: native core design

Status: approved on 2026-10-11.
License: Apache-2.0 (unchanged).

## 1. Intent

OpenComputeMesh is free software that anyone can run end to end on their own hardware. People pool the
compute of devices they already own into a mesh that serves AI models, with every token measured and
every credit accounted for.

Success for v0.2 means:

- One person can self-host a network with a single coordinator binary (or one container) and join
  devices with a single node binary or a desktop app, with no Python or Node.js installed.
- Devices on the same local network form a mesh with zero configuration.
- The mesh is safe among strangers: authenticated, attributable, rate-limited and spot-checked.
- Requests are scheduled onto the node expected to finish first, using measured performance.
- Every component that touches an outside system is a replaceable adapter.

## 2. Scope

### In v0.2

- Rust coordinator (`ocm-coord`) replacing the Python coordinator, feature-complete with v0.1:
  sessions, join codes, enrollment, nodes, jobs, streaming, receipts, ledger, benchmarks,
  throughput, OpenAI-compatible endpoint, admin, health.
- Rust node daemon (`ocm-node`) replacing both the Python agent and the v0.1 Rust agent.
- Load manager with expected-completion-time scoring, power-of-two-choices, warm-model affinity,
  admission control, circuit breakers.
- Local mesh: zero-config discovery on the LAN (mDNS), plus the existing federated coordinators.
- Runtime adapters: Ollama native API, any OpenAI-compatible server, Gemini API.
- Node identity (Ed25519) with signed result frames, reputation, and spot-check verification.
- Optional integrations behind Cargo features, off by default: TimescaleDB metrics sink, Sentry.
- Desktop app for macOS, Windows and Linux (Tauri 2) embedding the node daemon and the shared web UI.
- Coordinator container image and a compose file.
- Versioned releases with signed checksums for every binary.

### Out of v0.2 (planned for v0.3)

- iOS and Android apps with an embedded engine (llama.cpp on Metal, Vulkan or CPU).
- Postgres as the primary store.
- Cross-network federation (one request served by another coordinator's network).

### Never

- Running arbitrary code on nodes. Nodes only call their own runtime.
- Splitting one model across machines (tensor or pipeline parallelism over the internet).

## 3. Architecture

One Cargo workspace. Pure logic crates have no I/O so they are fast to test and fuzz.

```
crates/
  ocm-proto    wire types, protocol version 2, frame signing; no I/O
  ocm-sched    scheduler and load manager; pure functions over a snapshot
  ocm-runtime  RuntimeAdapter trait and adapters
  ocm-ledger   append-only ledger and job store on SQLite
  ocm-coord    coordinator binary
  ocm-node     node daemon binary and library (embedded by the desktop app)
apps/
  desktop      Tauri 2 shell
web/           React UI, built into the coordinator binary
```

Dependency direction: `proto` <- `sched`, `runtime`, `ledger` <- `coord`, `node` <- `apps/desktop`.
No crate depends on a binary crate. Process-wide state is passed explicitly as `Arc<AppState>`; the
only process-wide registry is the runtime adapter registry, built once at startup.

## 4. Protocol v2

- Transport: WebSocket over TLS (rustls). Browsers and nodes connect outbound to the coordinator.
- Frames: JSON with `v: 2`, `id`, `ts`. Unknown fields are rejected. Maximum frame size 1 MiB.
- Node frames carrying results (`job.completed`, `job.failed`, `job.metrics`) carry an Ed25519
  signature over the canonical frame bytes; the coordinator verifies against the node's registered key.
- Version negotiation in the first frame; a v1 client is refused with a clear upgrade message.

## 5. Load manager

Inputs per node: slots, active jobs, queued tokens, per-model EWMA of output tokens per second and of
time to first token, loaded models, error rate, reputation.

1. Filter: exact model digest, online, sharing, under owner limits, reputation above floor, breaker closed.
2. Score: expected completion = (queued tokens + estimated tokens) / EWMA tok/s + EWMA TTFT, with a
   cold-load penalty when the model is not loaded. Unknown nodes get a neutral prior.
3. Choose: power of two choices over eligible nodes (seeded RNG in tests), take the lower score.
4. Admission: bounded queue per model; when full, reject with `RETRY_LATER` and a retry hint.
5. Breaker: per node, opens on error rate over a sliding window, half-opens after a cool-down.
6. Retry: once, on another node, only if the first node never started the job.

## 6. Runtimes

`RuntimeAdapter`: `health`, `list_models`, `generate_stream(request, sink, cancel) -> Result`.
Adapters: `ollama` (loopback only), `openai_compat` (loopback by default, remote only with explicit
opt-in), `gemini` (cloud, explicit opt-in, key never leaves the node). Token counts carry provenance.

## 7. Security model

- Enrollment tokens: single use, short lived, exchanged for a node key registration.
- Node identity: Ed25519 key pair generated on the node, private key stored with 0600 permissions.
- Spot checks: the coordinator periodically sends the same seeded, temperature-0 prompt to at least
  three nodes reporting the same model digest. Prompt token counts must match exactly (tokenization is
  deterministic for a digest). Outputs are compared by similarity over the first 64 tokens, because
  floating-point differences across hardware can change later tokens for honest nodes. Reputation
  drops only when a node repeatedly disagrees with the majority.
- Limits: per member, node and IP rate limits; prompt and frame size limits; queue bounds.
- Privacy: prompts and outputs are never stored or logged; Sentry scrubbing as in v0.1.
- Browser: same-origin, Origin checks on writes, strict CSP, security headers.

## 8. Ledger

Unchanged invariants from v0.1: integer micro-credits, append-only (database triggers), idempotent
settlement, requester debit equals provider reward, settlement capped at the reservation and the cap
disclosed on the receipt, consistency checker.

## 9. Desktop app

Tauri 2 shell with the shared web UI, the embedded node daemon, tray controls (share, pause, quit),
start at login, and a live view of the device's contribution.

## 10. Packaging and versions

- Semantic versioning; one workspace version; `CHANGELOG.md` in Keep a Changelog format.
- Conventional commit subjects; releases are tags `vX.Y.Z` that trigger the release workflow.
- Release workflow builds `ocm-coord` and `ocm-node` for macOS (arm64, x86_64), Linux (x86_64,
  arm64, static musl) and Windows (x86_64), desktop installers, and publishes SHA-256 checksums.
- Container: multi-arch `ocm-coord` image from a static binary on a distroless base, non-root.
- `compose.yaml`: coordinator, plus optional TimescaleDB under a profile.

## 11. Dependencies

Each dependency must be justified in `docs/DEPENDENCIES.md`, default features disabled where possible.
Runtime set: tokio, axum (including its WebSocket support), rustls, serde, serde_json, rusqlite (bundled),
reqwest (rustls), ed25519-dalek, rand, tracing, clap, mdns-sd. Optional: tokio-postgres (metrics sink),
sentry. Dev only: proptest, criterion, cargo-fuzz targets.

## 12. Quality gates

All gates run in CI on macOS, Linux and Windows; a red gate blocks merge.

- Rust: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo deny check`,
  `cargo test --workspace`.
- Property tests: scheduler (never picks an ineligible node; score monotonic in queued tokens) and
  ledger (debit equals reward per job; balances equal entry sums; no double settlement).
- Fuzzing: every frame decoder for at least 60 seconds per target in CI.
- End to end: coordinator, two nodes and a fake runtime as real processes over real sockets, covering
  join, enroll, route, stream, cancel, timeout, disconnect, retry, settlement and spot checks.
- Web: strict TypeScript, Biome lint and format, Playwright flows for join, run, receipt and nodes.
- Performance budgets (benchmarks fail CI when exceeded): scheduler decision under 50 microseconds
  at 10,000 nodes; coordinator sustains 1,000 concurrent streams; relay adds under 1 ms per token.
- Staleness: a release checklist step verifies that README, docs, CLI help and `.env.example` match
  the code, and that no removed component is still referenced.

## 13. Acceptance criteria for v0.2

1. `ocm-coord` and `ocm-node` pass every v0.1 behaviour test, ported to the Rust end-to-end suite.
2. Two nodes on one LAN discover each other and serve a request with no coordinator URL configured.
3. With nodes of different measured speeds, the load manager routes more work to the faster node and
   keeps p95 queue wait below the admission bound under a 10x burst.
4. A node returning altered output or a wrong prompt token count across repeated spot checks has its
   reputation lowered and stops receiving work after the configured threshold, while honest nodes on
   different hardware are not penalised in the same test.
5. A forged result frame (bad signature) is rejected and logged without content.
6. The container image runs as non-root, is under 30 MB, and passes `/readyz`.
7. The desktop app installs, enrolls, shares a local model and pauses from the tray on all three OSes.
8. Every gate in section 12 is green on all three CI operating systems.
9. The staleness check passes; the Python coordinator and agents are removed from the tree.

## 14. Repo hygiene

The repository contains only OpenComputeMesh. Hackathon framing, judging maps, sponsor-promotion
wording and the demo video project are removed; integrations remain as neutral optional adapters.

## 15. Patents

The project stays under Apache-2.0, whose section 3 grants every user a patent license from each
contributor and terminates that license for anyone who files patent litigation over the work. Designs,
specs and code are published promptly in this public repository with dated commits and tagged releases,
so they serve as prior art against later patent claims on what is published here. Contributions are
accepted only under Apache-2.0 (no separate contributor license agreement that could reassign rights).

## 16. Delivery

Work is planned as independent streams that parallel subagents execute, each with a task review and
a final whole-branch review: (a) proto + sched, (b) runtime adapters, (c) ledger + coord, (d) node
daemon + discovery, (e) web + desktop app, (f) packaging, CI and docs.
